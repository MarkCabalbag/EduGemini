## 1. Purpose and how to use this brief

This brief is the design reference for the web app. Wherever a question is about how something looks, feels, or behaves, the answer should be here. Where it isn't, the App Flow decides the behavior and this brief decides the presentation.

Rules for the team:
- **Behavior and copy come from the App Flow.** When this brief quotes a string, it matches the App Flow exactly. New strings are marked **(new)** and need owner approval.
- **Tokens, not hex values, in code.** Components reference the tokens in Section 5.
- **Contrast is verified by script, not by eye.** The table in Section 5.4 is generated by the script in Appendix A. Re-run it whenever a token changes.

## 2. Users and context of use

| User | Typical device and place | What they need from a screen | Emotional moments to design for |
|---|---|---|---|
| **Instructor** (Maya) | Laptop, at a desk, often reviewing 30 to 150 submissions in one sitting | Speed, a clear queue, the original file next to the AI score, confidence that nothing was approved by accident | Seeing AI scores she doesn't trust; the fear of approving something wrong; quota running out mid-batch |
| **Student** (Jon) | Phone, often a photo of handwritten work, sometimes on a bus | Certainty that the upload worked, an understandable result, knowing how many tries are left | Waiting for a grade; a failed upload; a grade he disagrees with; being locked out after approval |
| **Super Admin** | Laptop, rare visits | Platform health at a glance; safe, deliberate actions | Irreversible actions (delete); suspending a user |

**The product must make a stressful moment feel handled.** Every status message says what happened, what it means for the user, and what to do next. Nothing is shown as a failure the student caused.

---

## 3. Design principles

1. **AI is always labeled and never final.** Every AI score and feedback block carries the "AI-generated" chip and the disclosure line. An instructor's approval is the only thing that makes a grade final, and the UI shows that clearly.
2. **Status is always visible.** Every submission, class, and assignment shows its current state in words, not only color or icons.
3. **Never lose a user's work.** Drafts autosave. Uploads survive a dropped connection. Typed text survives an error. A "failed" state always offers a retry.
4. **Calm, plain language.** Short sentences. No blame. No jargon such as "exception" or "error code" in user copy. Technical detail goes in logs, not in the UI.
5. **Fast for repeat work.** Instructors do the same actions dozens of times. Keyboard paths, sticky action bars, and "next item" navigation matter more than decoration.
6. **Phone-first and accessible.** Students upload from phones. Every flow works at 360 px wide and with a keyboard or a screen reader.

## 4. Visual direction

- **Mood:** calm, trustworthy, and quiet. The product handles grades, so it should feel like a careful tool, not a playful app.
- **Color:** neutral slate for structure, indigo as the primary brand color, and a restrained set of status colors (Section 5). Color carries meaning, never alone (Section 8).
- **Space:** generous whitespace; a 4 px base unit; content sits in a single column up to 1,120 px wide on desktop.
- **Shape:** 8 px corner radius on cards and inputs, 6 px on chips, no heavy shadows (a 1 px border and a very soft shadow on raised surfaces only).
- **Type:** Inter, self-hosted (OFL license), with the system UI font as fallback. Scale in Section 4.1.
- **Icons:** lucide-react, 16 px in text, 20 px in buttons, always paired with a text label on the primary actions.
- **Imagery:** none in v1 except the user's own uploaded files. No stock photos, no decorative illustration.

### 4.1 Type scale

| Token | Size / line height | Weight | Used for |
|---|---|---|---|
| `text-display` | 28 / 34 | 600 | Page titles (one per page) |
| `text-title` | 20 / 28 | 600 | Section headings, card titles |
| `text-body` | 16 / 24 | 400 | Body text, feedback, form fields |
| `text-body-strong` | 16 / 24 | 600 | Labels, emphasized values such as scores |
| `text-small` | 14 / 20 | 400 | Helper text, timestamps, table cells |
| `text-micro` | 12 / 16 | 500 | Chip labels only |

Body text never goes below 16 px on phones. Feedback text uses `text-body` with 1.6 line height for readability.

## 6. Layout and navigation

### 6.1 App shell
- **Header** (all signed-in screens): logo or wordmark on the left; on the right, in order: **Review Queue** (instructors only, with a count badge), **Notifications** (bell with the unread count beside it when above zero), **Settings**, and the account menu. Matches the App Flow Navigation Map.
- **Class pages** add a second row of tabs: Overview, Assignments, People, Gradebook, Announcements (Could). Tabs scroll horizontally on phones rather than wrapping.
- **Breadcrumb** under the header on deep pages (for example `Biology 101 / Essay 2 / Ana L.`). On phones, show only the back arrow and the current page name.
- **Super Admin** uses a separate layout with a left sidebar: Accounts, Classes, Platform health, Audit log. It never shares the instructor or student header.

### 6.2 Breakpoints and content width

| Name | Width | Layout behavior |
|---|---|---|
| Phone | 360 to 767 px | Single column; tables become stacked cards; sticky bottom action bar where a page has one primary action |
| Tablet | 768 to 1023 px | Two columns where it helps (class cards); side-by-side review starts at 1024 px |
| Desktop | 1024 px and up | Full layout; side-by-side Submission screen; tables with all columns |
| Wide | 1280 px and up | Content max width 1,120 px, centered |

Minimum supported width is 360 px. No horizontal page scroll at any width. Tables that can't fit scroll inside their own container, with a visible scroll hint.

### 6.3 Mobile navigation
- Bottom tab bar is **not** used in v1 (the App Flow has few top-level destinations, and header access is enough). The header collapses to a logo, the bell, and a menu button; the menu holds Review Queue, Settings, and sign-out.
- Students see fewer items: Classes, Notifications, Settings.

## 8. Status chip specification

The chip is the only way the product states a submission's or enrollment's condition. Every status in the PRD appears here.

### 8.1 Submission states (PRD Section 8.1)

| State | Instructor sees (chip) | Student sees (chip) | Token | Notes |
|---|---|---|---|---|
| Uploading | Not visible in the instructor's view | "Uploading" with progress | `status-pending` | Progress bar, not just the chip |
| Queued | "Grading in progress" | "Grading in progress" | `status-pending` | Plus the note "usually about a minute" on the student side (Section 11.2) |
| Grading | "Grading in progress" | "Grading in progress" | `status-pending` | Same as Queued in v1; no separate chip needed |
| AI-generated | "AI-generated" | "AI-generated" | `status-ai` | Student also sees the disclosure line (Section 11.3) |
| Needs manual review | "Needs review" with the cause in text (for example "AI failed after retries", "Key needs attention", "Quota reached") | "Awaiting instructor review" | Instructor: `status-review`. Student: `status-pending` | The student chip never uses `status-error` |
| File error | Not visible in the instructor's view | "File needs re-upload" with the reason | `status-error` | Shown in the upload area, not as a submission chip (no valid submission exists) |
| Instructor-approved | "Instructor-approved" | "Instructor-approved" | `status-approved` | Locked; student sees a lock icon beside it |

### 8.2 Derived flags (layered on any state; PRD Section 8.1 note)

| Flag | Label | Token | Shown where |
|---|---|---|---|
| Late | "Late" | `status-late` | Next to the submission state (both views) |
| Re-grade pending | "Re-grade pending review" | `status-ai` | Instructor queue and Submission screen; student sees the approved chip unchanged |
| Criteria changed | "Criteria changed since approval" | `status-review` | Tracker and Submission screen (instructor only) |
| Late closed | "Closed" | `status-info` | Student assignment row when late submissions are closed |

### 8.3 Tracker views (not states; PRD Section 8.1 note)

| View | Label | Token |
|---|---|---|
| No submission, past due | "Missing" | `status-error` (instructor tracker only; never shown to students) |
| No submission, before due | "Not yet due" | `status-info` |
| Any valid submission | "Turned in" (count) | `status-approved` for the count tile only |

### 8.4 Enrollment states (PRD Section 8.3)

| State | Label | Token | Shown to |
|---|---|---|---|
| Active | "Approved" | `status-approved` | Instructor and student (the App Flow uses "Approved" for users) |
| Pending | "Pending" or "Pending approval" | `status-pending` | Student ("Pending approval"); instructor People view ("Pending") |
| Declined | "Declined" | `status-info` | Student and instructor |
| Removed | "Removed" | `status-info` | Instructor only (students see no class) |

### 8.5 Class and assignment status

| Object and state | Label | Token |
|---|---|---|
| Class archived | "Archived" | `status-info` |
| Assignment draft | "Draft" | `status-pending` (instructor only) |
| Assignment archived | "Archived" | `status-info` |
| Assignment published | No chip; shown as normal text | — |
| Class temporarily unavailable (instructor suspended) | "Temporarily unavailable" | `status-review` (student view) |

**Rule for all chips:** text first, icon second, color third. Chips never rely on color alone. The label is the accessible name.

## 10. Interaction patterns

### 10.1 Forms
- **Validate on blur and on submit**, not on every keystroke, except for password strength (live checklist) and score input (live range check).
- Errors appear beneath the field in `status-error` text with an icon, and the field outline changes color and thickness. The error message names the fix ("Enter a score from 0 to 50").
- Submit buttons stay enabled; the error explains what is missing. Disabled buttons are used only for the upload Submit (with a reason shown beside it).

### 10.2 Destructive actions
- Delete, remove student, archive class, regenerate or disable the class code, delete class, delete assignment, and delete account use `ConfirmDialog`.
- The dialog states the consequence with counts where the PRD requires them ("This removes 28 students' submissions and 3 assignments.").
- Typed confirmation is required for: class deletion (class name), account deletion (`DELETE`), and assignment deletion (assignment name). Other confirmations are a plain "Remove" button with the destructive style.
- The destructive button is never the default focused button in the dialog.

### 10.3 File upload states
Each file row moves through: **Ready** → **Uploading (with percent)** → **Stored** (check icon) or **Couldn't upload** (with Retry) or **Rejected** (with the reason from the App Flow: type not supported, too large, too many pages, password-protected, unreadable). A retry keeps the rest of the files.

### 10.4 Loading
- Pages show `Skeleton` blocks shaped like the final content within 200 ms of navigation.
- Buttons that trigger requests show a spinner and keep their label. Repeated taps are ignored while pending.
- Waiting longer than 3 seconds on a list shows a short line: "Still loading…"

### 10.5 Grading status (live updates)
- The student's result area updates in place when grading finishes. Nothing else on the page shifts.
- A polite live region announces: "Your result is ready." Not announced on every poll, only on the change.
- A "Grading in progress" block has a subtle animated indicator, switched off under reduced motion (the text stays).
- If grading is delayed by pacing, the note changes to "Grading is taking longer than usual." (PRD Section 9.5.)

### 10.6 Toasts versus inline messages
- **Toasts:** confirmations ("Saved", "Code copied"). They disappear after 4 seconds, do not take focus, and are announced politely.
- **Inline:** every error, every state change that matters (a locked submission, a key problem), and every instruction. Nothing important lives only in a toast.

### 10.7 Keyboard (Could for shortcuts; required for operability)
- Required: every control is reachable and operable with Tab, Shift+Tab, Enter, Space, and arrow keys where a widget calls for them.
- Review shortcuts (Could): `J` and `K` for next and previous item, `A` to approve when the form is valid, `E` to edit score. Shown in a `?` help dialog. Never active while typing in a field.

### 10.8 Empty states

| Where | Copy | Action |
|---|---|---|
| Instructor dashboard, no classes | "No classes yet. Create one to share a code with your students." | Create class |
| Student dashboard, no classes | "You haven't joined a class yet. Enter the code your instructor gave you." | Join a class input |
| Class, no assignments (instructor) | "Create your first assignment." | New assignment |
| Class, no assignments (student) | "No assignments yet." | None |

### 10.9 Confirmation of AI actions
- "Re-run AI" and "Re-run AI grading on N submissions" always state that it uses the instructor's Gemini quota (PRD FR-KEY-05, FR-ASG-04).
- Approving a grade never happens on a single tap in a list; it happens on the Submission screen or in bulk after a confirmation.

## 11. Content and microcopy

### 11.1 Voice
- **Plain and calm.** Short sentences. Say what happened, what it means, what to do next.
- **No blame.** Never "you failed" or "you didn't". Say "the upload didn't finish" or "this file couldn't be read."
- **Honest about AI.** Say "AI-generated" and "reviewed by your instructor," not "graded by AI" or "auto-graded." Never imply the AI is final.
- **Second person** for users ("your submission", "your instructor"). Instructors are addressed as "you" too.
- **Sentence case** for all headings, buttons, and labels.
- No exclamation marks in system messages. No emoji in product copy.

The page the item opens shows it instead, in its full-page form ("This item is no longer available." with "Go to dashboard"). A page reached any other way still says "We couldn't find that page."

## 12. Accessibility

Target: **WCAG 2.1 AA** for every core flow (PRD Section 12). This checklist is the review gate for every screen.

- [ ] **Contrast** meets the table in Section 5.4 in both themes (checked by script).
- [ ] **Focus** is always visible: 2 px `--focus-ring` with a 2 px offset. Never removed by CSS.
- [ ] **Touch targets** are at least 44 by 44 px on phones, including chip-adjacent buttons and the file row controls.
- [ ] **Labels** are visible text, associated with their inputs. Placeholder text is never the only label.
- [ ] **Errors** are identified in text, linked to their field (`aria-describedby`), and announced.
- [ ] **Status** is conveyed in text (chips include labels), never color alone.
- [ ] **Live updates** (grading, upload progress) use an `aria-live="polite"` region and announce only meaningful changes.
- [ ] **Dialogs** trap focus, return focus to the trigger on close, and close with Escape (except during a running request).
- [ ] **Keyboard:** every flow works without a mouse, including file reorder (↑ and ↓ buttons), tabs (arrow keys), and approval.
- [ ] **Reduced motion:** all animation is off under `prefers-reduced-motion`; progress text remains.
- [ ] **Headings** form a logical outline; one `h1` per page.
- [ ] **Images and icons:** decorative icons are hidden from assistive tech; informational icons have text alternatives.
- [ ] **Uploaded files:** the file name and status are read as text; thumbnails have alt text "Page 2 of Ana's essay" or the file name.
- [ ] **PDF viewer:** page changes announced; navigation buttons labeled ("Previous page", "Next page").
- [ ] **Language:** `lang="en"` on the document.
- [ ] **Zoom:** content reflows at 200% zoom and 320 px width without horizontal scroll.

## 14. Motion

- **Allowed:** short opacity fades (150 ms) when content appears; a progress bar; the grading indicator.
- **Not used:** page transitions, parallax, bouncing, autoplay, or decorative loops.
- Under `prefers-reduced-motion: reduce`, all transitions are instant, and the grading indicator becomes static text.

## 15. Theming implementation

- Tailwind v4 `@custom-variant dark`. A `dark` class on the root element switches the tokens in Section 5.
- **Default:** follows the operating system setting (`prefers-color-scheme`).
- **Manual override:** Settings > Account > Appearance offers System, Light, and Dark. The choice is stored in `localStorage` (a per-browser preference; it is not sensitive, and a failed read falls back to System).
- **No flash of the wrong theme:** a small same-origin script in the document head (`public/theme-init.js`, not inline, because the CSP allows `script-src 'self'` only) reads the stored choice and sets the class before the first paint.
- Every component uses tokens, never literal colors. A lint rule forbids hex values in component files.
- Images and the PDF viewer keep their own backgrounds; the viewer frame uses `--surface` so the page edge is visible in dark mode.
